# Управление процессами

**Область:** общие правила управления длительными задачами. Runner и его гарантии определяются проектом. Например, у [Zanevka MCP v2](https://github.com/Ed1ch/zanevka-mcp-v2/blob/main/docs/operations/codex-runner.md) есть принятый runner с блокировками в пределах одного Linux-хоста/UID, постоянными сессиями, ручными `resume`/`recover` и приватными журналами. Он не координирует ручные процессы вне runner и другие хосты/UID.

## Общие правила для агента
- Перед запуском Codex или другого долгого задания проверь активные экземпляры именно этой задачи в нужном workspace.
- После timeout/disconnect статус **неизвестен**: сначала проверь, выполняется ли предыдущая попытка. Не делай повторный запуск вслепую.
- Останавливай только процессы своей попытки по проверенной принадлежности; не завершай все процессы с именем `codex`, `codex.exe`, `bash` или `powershell.exe` по имени.

## Рекомендации для новых runner

Это требования к проектированию, а не гарантия существования общего сервиса.
- Идентичность: `host_id`, `task_id`, нормализованный `workspace_identity`, `attempt_id`; idempotency key для операции.
- Перед spawn — межпроцессная блокировка и запись попытки. Повтор возвращает existing attempt, а не запускает вторую копию.
- Привязка к процессу: PID + время создания + executable + владелец/Job Object. PID или файл `.lock` по отдельности ненадёжны.
- Состояния: `planned → approved → starting → running → stopping → succeeded/failed/cancelled/unknown`.
- `unknown` не разрешает повторный запуск; хранить результат и журнал без секретов.
- Между разными хостами гарантия единственности появится только с общим координатором.

Проверки: одновременные старты → один процесс; timeout → без дубликата; остановка → чужие процессы/VM/туннели не затронуты.
